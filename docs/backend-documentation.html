Backend documentation

The Manzili API, rebuilt in .NET.

A multi-vendor marketplace for handmade Egyptian products — ported from Node/Express/Prisma to ASP.NET Core with full feature parity, running against the very same PostgreSQL database.

Runtime
.NET 10 (LTS) · ASP.NET Core controller Web API
Data
EF Core 10 · Npgsql · PostgreSQL (database-first)
Auth
JWT (HS256) in httpOnly cookies · BCrypt — buyer/seller and admin sessions isolated
Integrations
Stripe · Cloudinary · Bosta · SMTP email
Surface
5 projects · ~95 endpoints · 47 entities · ~28 services · 4 layers
New to .NET? Read this first

This backend is a web server that answers HTTP requests with JSON. The code is organised as a solution (Manzili.sln) made of several projects. Terms you don't recognise are defined in the Glossary; the rose-coloured Expert notes add depth and can be hidden with the control at the top right.

Expert note

A pragmatic Clean-Architecture-lite split (Domain / Application / Infrastructure / Api). Because the port is database-first, generated POCO entities and concrete services both live in Infrastructure; controllers depend on them directly via DI. Mockability is traded for velocity and recovered through WebApplicationFactory integration tests.

Quick start

You need the .NET 10 SDK. Secrets (DB connection, JWT, Stripe/Cloudinary/Bosta keys) come from user-secrets in development — nothing sensitive is committed.

bash

dotnet build
dotnet run --project src/Manzili.Api          # Development env loads user-secrets

# Swagger UI : https://localhost:<port>/swagger
# Health     : GET /api/v1/health -> { "success": true, "data": { "status": "ok", "database": "connected" } }

Architecture

Four layers, one direction

Outer layers know about inner layers, never the reverse — a kitchen where the waiter never cooks and the kitchen never talks to customers.

Manzili.Api

The HTTP edge — controllers, the middleware pipeline, JWT + CORS, and Program.cs, the composition root that wires everything together.

Manzili.Application

The shared contract — request/response DTOs, validators, strongly-typed options, ported helpers (status maps, pagination, error types). No database knowledge.

Manzili.Infrastructure

The "how" — the EF Core DbContext, the 47 scaffolded entities, every feature service, and the external integrations. The only layer that touches the database or the network.

Manzili.Domain

Reserved for pure domain types; minimal here because the data model is generated from the existing schema.

Expert note — dependency direction

References flow Api → Application, Infrastructure; Infrastructure → Application, Domain; Application → Domain. DTOs sit in Application so producing services and returning controllers both see them without an inward dependency. Each feature self-registers via an Add{Feature}() extension that AddInfrastructure() calls, keeping Program.cs stable as features grow.

Request lifecycle

What happens to GET /api/v1/users/me carrying the auth cookie:

  1. Exception middleware wraps the whole pipeline so any thrown error becomes a clean JSON envelope.
  2. CORS → Authentication (validate JWT, populate claims) → Authorization ([Authorize]).
  3. Routing dispatches to UsersController.Me().
  4. The controller reads CurrentPersonId and calls UserService.
  5. The service queries through ManziliDbContext (EF Core → SQL → PostgreSQL).
  6. The controller returns ApiOk(dto) → { success: true, data: {…} }.
Expert note — middleware order

The exception handler is registered first so it surrounds auth. CORS precedes auth; UseAuthentication() precedes UseAuthorization(). The JWT handler runs with MapInboundClaims = false so sub/role/sellerId stay as raw claim names.

Core concept

The response envelope

One consistent shape on every response, ported verbatim so the frontend contract is unchanged.

json
{ "success": true, "data": { "id": "42", "name": "Ada", "email": "ada@example.com" } }

Extra fields (pagination, tokens) merge at the top level, not under data:

json
{ "success": true, "data": { "ProductCards": [ … ] }, "total": 120, "page": 1, "limit": 20 }
json
{ "success": false, "error": { "message": "Validation failed", "code": "VALIDATION_ERROR",
    "details": [ { "path": "Email", "message": "'Email' is not a valid email address." } ] } }

Controllers never hand-build this — they inherit ApiController:

C#
protected IActionResult ApiOk(object? data, IDictionary<string, object?>? meta = null, int statusCode = 200)
{
    var payload = new Dictionary<string, object?> { ["success"] = true, ["data"] = data };
    if (meta is not null)
        foreach (var (key, value) in meta) payload[key] = value;   // merge meta at top level
    return StatusCode(statusCode, payload);
}
Expert note — why a Dictionary root

System.Text.Json serialises dictionary keys verbatim (no camelCase transform), so keys like "ProductCards" and "refreshToken" match the Node output exactly, while nested DTOs keep the default camelCase. OpenAPI fields containing spaces (e.g. "main image") use [JsonPropertyName].

Core concept

Authentication & JWT

register, login and refresh issue a short-lived access token (15 min) and a long-lived refresh token (7 days). Both are set as httpOnly cookies — never returned to JS and never stored in localStorage — so the browser attaches them automatically and a script can't read them.

What is a JWT?

A signed string the server issues on login. The server verifies the signature with a secret key and then trusts the facts inside (who you are, your role) without a database lookup. "Signed" means tampering is detectable — not that the contents are secret. Here the JWT travels in an httpOnly cookie (not an Authorization header), so it is invisible to page JavaScript.

Admin sessions are isolated

Buyer/seller sessions use the cookies manzili_at (access) + manzili_rt (refresh) at path /. The admin portal uses a separate pair — manzili_admin_at + manzili_admin_rt — path-scoped to /api/v1/admin. So an admin session and a buyer/seller session are fully isolated and can coexist in one browser; logging into the admin portal can no longer clobber a buyer or seller session (this fixed a real bug). The JWT cookie extractor in Program.cs is path-aware: on /api/v1/admin/* it reads the admin cookie, elsewhere the normal one.

C# — role resolution on login
private async Task<(string Role, int? SellerId)> DetermineRoleAsync(int personId)
{
    if (await _db.Systemadmins.AnyAsync(a => a.Personid == personId)) return ("admin", null);
    var seller = await _db.Sellers.FirstOrDefaultAsync(s => s.Personid == personId);
    if (seller is not null) return ("seller", seller.Sellerid);
    return ("buyer", null);
}
Expert note — BCrypt & HS256 interop

Passwords use BCrypt.Net-Next (work factor 10) which verifies $2a$/$2b$/$2y$ hashes, so Node-created accounts log in unchanged. Tokens are HS256-signed with the same UTF-8 secret bytes as jsonwebtoken, so a token minted by either stack validates on the other. The refresh token is also stored on person.refresh_token and compared on refresh — a server-side revocation hook.

C# — token validation parameters
new TokenValidationParameters
{
    ValidateIssuer = false,                 // single-audience internal API
    ValidateAudience = false,
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret)),
    ValidateLifetime = true,
    ClockSkew = TimeSpan.FromSeconds(5),    // tight; default is 5 minutes
    NameClaimType = "sub",
    RoleClaimType = "role",                 // makes [Authorize(Roles=…)] read our claim
}
Expert note — signing key & skew

HS256 keys must be at least 256 bits — the configured secrets comfortably exceed that as UTF-8 bytes. Issuer/audience validation is disabled because both stacks issue tokens for one internal audience; ClockSkew is dropped from the 5-minute default to 5 seconds so expiry is enforced tightly. RoleClaimType = "role" is what lets [Authorize(Roles="seller")] match the raw role claim.

Gotcha that bit us

JwtSecurityTokenHandler remaps sub to a long URI by default, so FindFirst("sub") returned null. Fixed with MapInboundClaims = false on both the bearer options and the manual refresh validation.

Core concept

The data layer (EF Core)

What is EF Core?

An ORM — it lets you query the database with C# instead of raw SQL. It is the .NET counterpart to Prisma in the old backend. db.Products.Where(p => p.InStock).ToListAsync() becomes a SELECT … WHERE ….

This is database-first: the existing schema was reverse-engineered into 47 entities + a ManziliDbContext.

bash — one-time scaffold
dotnet ef dbcontext scaffold "<connection>" Npgsql.EntityFrameworkCore.PostgreSQL \
  --schema manzili --context ManziliDbContext \
  --context-dir Persistence --output-dir Persistence/Entities --no-onconfiguring
C# — using it
public sealed class ProductService(ManziliDbContext db)
{
    public Task<Product?> GetAsync(int id) =>
        db.Products
          .Include(p => p.ProductImages)
          .AsNoTracking()                       // read-only: skip change tracking
          .FirstOrDefaultAsync(p => p.Productid == id);
}

Snake_case columns become PascalCase: first_name → FirstName, created_at → CreatedAt.

Pagination

List endpoints share one helper, ported from the Node parsePagination: page is at least 1, limit is clamped to 1–100 (default 20), and Skip/Take are derived for the query.

C#
public static Pagination Parse(int? page, int? limit)
{
    var p = Math.Max(1, page ?? 1);
    var l = Math.Min(100, Math.Max(1, limit ?? 20));
    return new Pagination(p, l, (p - 1) * l, l);   // Page, Limit, Skip, Take
}
// usage:  var pg = Pagination.Parse(page, limit);
//         var items = await query.Skip(pg.Skip).Take(pg.Take).ToListAsync();
Expert note — connection & SSL

The connection string targets the Supabase pooler with Ssl Mode=Require. The DbContext is registered with UseNpgsql(connectionString) and the string itself never lands in source — it comes from ConnectionStrings:Default in user-secrets (dev) or the ConnectionStrings__Default env var (prod). Migrations are intentionally not used: the schema is owned upstream and reverse-engineered, so the app treats it as read/write but never re-shapes it.

Expert note — tracking, transactions, lifetimes

Reads use AsNoTracking(); atomic writes wrap work in BeginTransactionAsync() (EF's $transaction). DbContext is scoped (one per request); DB-bound services are scoped, stateless helpers are singletons.

One schema fix was required

Scaffolding failed on a single FK type mismatch — custom_request.categoryid was integer while category.categoryid is smallint. A one-line ALTER COLUMN … TYPE smallint aligned the DB with its own Prisma declaration.

Gotcha — timestamp without time zone + Npgsql

Several legacy columns are timestamp without time zone — notably coupons.created_at, reports.created_at/resolved_at, notification.created_at, and store_pickup_addresses. Npgsql maps those to a local DateTime and throws if you hand it a DateTime whose Kind is Utc (which is what DateTime.UtcNow produces). Every write to those columns therefore uses DateTime.SpecifyKind(value, DateTimeKind.Unspecified); the read path re-stamps with Utc. This silently 500-ed every notification create until it was fixed across NotificationService, CouponService, AdminService and ReportService.

FluentValidation replaces the Zod schemas. Validators are auto-discovered; a base-controller helper runs them and throws a 400 with a details array.

Deep dive

Order splitting

A single cart can hold items from several sellers. One order splits into one store_order per seller, each with its own line items.

The cart is account-linked, not browser-stored

The cart is persisted server-side and tied to the account — it is no longer kept in the browser / localStorage. It survives logout and follows the account across devices, and a guest's in-session cart is merged into the account on login / register / Google sign-in. CartController at /api/v1/cart exposes GET (load), PUT (replace), POST /cart/merge (merge a guest cart, summing quantities) and DELETE (clear). CartService stores the cart as a variant-faithful JSON snapshot in a new items_json column on the cart table (added idempotently by SchemaMigrator). The cart is re-priced server-side at checkout, so stored line hints can't drive a wrong charge.

model
order  (totals, payment method/status, address)
 ├─ store_order  (seller A)  → store_order_items[]   (price_at_purchase snapshot)
 └─ store_order  (seller B)  → store_order_items[]
  • Items are grouped by seller in first-seen order (insertion-ordered, like the JS Map).
  • Price, name and image are snapshotted per line, so history survives later product edits.
  • Discount is split pro-rata by subtotal, rounded to 2 dp away-from-zero.
  • Stock is decremented; the whole thing runs in one transaction and the order is re-read after commit.
Expert note

Order status follows payment method (STRIPE → 0 PENDING_PAYMENT, COD → 1 ORDER_PLACED). The coupon is stored as a JSON coupon_snapshot and the client-supplied discount is trusted, exactly as Node did — a faithful parity decision, flagged rather than endorsed.

Deep dive

Wallet idempotency

Each seller has a wallet with a pending and an available balance plus an immutable ledger.

Why idempotency?

A webhook or retry might deliver the same "credit the seller" event twice. Idempotency means doing it twice has the same effect as once — so money is never double-counted.

C# — the guard
var already = await db.WalletTransactions
    .AnyAsync(t => t.WalletId == walletId && t.IdempotencyKey == key);
if (already) return PostResult.Skipped;        // do NOT touch the balance
// else: insert the ledger row AND adjust the bucket balance inside one transaction.
Expert note

Buckets: PENDING → PendingBalance, else AvailableBalance; a payout posts a negative available amount and is rejected if funds are insufficient. The unique (wallet_id, idempotency_key) constraint is the real backstop — even under a race the DB rejects the duplicate and the balance change rolls back with it. Ledger rows are only inserted, never updated.

Deep dive

Webhooks & the raw body

Stripe signs each webhook against the exact raw bytes it sent. If middleware re-serialises the JSON first, the signature breaks.

C#
[HttpPost("stripe"), AllowAnonymous]
public async Task<IActionResult> Stripe()
{
    var json = await new StreamReader(Request.Body).ReadToEndAsync();   // raw, unparsed
    var evt = EventUtility.ConstructEvent(json, Request.Headers["Stripe-Signature"], _webhookSecret);
    if (evt.Type == "checkout.session.completed") { /* mark order paid, update store_orders */ }
    return Ok(new { received = true });
}
Expert note

The action takes no body-bound parameter, so MVC model binding never consumes the stream. Webhook responses return plain { received: true } (not the envelope), as Stripe/Bosta expect. Bosta webhooks are de-duplicated by a SHA-256 hash of the payload stored per shipment in shipment_events under a unique constraint.

Operational note

Stripe verification needs Manzili:Stripe:WebhookSecret set, otherwise the webhook returns 400.

Platform capability

Fulfillment lifecycle

Once a payment is confirmed, FulfillmentService turns the paid order into real, trackable shipments — one per seller — and keeps the buyer, the seller and the wallet in sync as parcels move.

The story in one line

Buyer pays → each seller gets a delivery booked with the courier (Bosta) and a tracking number → seller is told to prepare the parcel, buyer gets the tracking link → when it is delivered, the seller's money unlocks and the buyer can leave a review.

No phantom orders — paid means placed

An online-payment order (Stripe / Mobile Wallet / Fawry) only appears as a real placed order once it is actually PAID. Unpaid/abandoned online orders, and canceled orders, are filtered out of both the buyer's orders list and the seller's orders list. COD is the exception (pay-on-delivery → shown immediately). Abandoned gateway attempts are cancelled server-side and never leave a phantom order.

What the orders list returns

The orders list DTO carries a per-vendor breakdown storeOrders[] — each with storeName, its items (including imageUrl), the delivery total, and the Bosta shipment + tracking timeline — plus the delivery address. The buyer's orders page renders one rich card per vendor, with item thumbnails, per-vendor delivery, and a status timeline.

On payment confirmed

The single entry point is MarkOrderPaidAndFulfillAsync — called by both the Stripe webhook and the POST /checkout/confirm endpoint, and idempotent so running it twice is harmless. For each store_order it:

  • Books one Bosta delivery (BostaClient.CreateDeliveryAsync) collecting from the seller's default warehouse, and persists a Shipment with its tracking number and carrier.
  • Bosta is required — no fake fallback. If Bosta isn't connected (BostaOptions.IntegrationEnabled = false / no auth) or the create-delivery call fails, fulfillment errors (BOSTA_NOT_CONNECTED / BOSTA_DELIVERY_FAILED) rather than minting a synthetic tracking number — a Shipment only ever reflects a real Bosta delivery.
  • Seeds a ShipmentEvent timeline (the first "created/processing" rows).
  • Moves the store-order to PROCESSING, posts the seller's wallet SALE_CREDIT + SHIPPING_DEBIT as pending funds, and notifies the seller ("prepare pickup") and the buyer ("track your order").

Status transitions

A store-order advances through SHIPPED → DELIVERED via one shared method, TransitionStoreOrderStatusAsync, driven from two sources:

TriggerEffect
PATCH /seller/orders/{id}/statusSeller marks the parcel shipped / delivered by hand.
POST /webhooks/bostaThe courier's webhook reports real movement (deduped per shipment).

On SHIPPED the buyer is notified; on DELIVERED the seller's pending wallet funds are released to available, the buyer is told they can now review, and reviews unlock once RollupOrderStatusAsync aggregates the seller's store-orders up to a DELIVERED parent order.

Why a separate confirm endpoint?

Webhooks can be delayed or blocked in local development. POST /checkout/confirm lets the success page verify the Stripe session server-side and fulfill immediately — without waiting for Stripe to call back. Because both paths run the same idempotent method, whichever fires first wins and the second is a no-op.

Expert note — webhook-independent confirmation

The frontend's /orders page calls /checkout/confirm on the ?session_id= return. ConfirmSessionAsync re-fetches the session from Stripe (it does not trust the client), checks payment_status == "paid", then delegates to MarkOrderPaidAndFulfillAsync — the exact code path the webhook uses. Custom-order milestones reuse the same machinery: paying the final milestone creates a real Order + StoreOrder (backed by a hidden, disabled placeholder product to satisfy the line-item FK) and runs the identical pipeline.

Platform commission — standard order15% of goodsSeller (deducted from payout)

Bosta shipping — seller share65%Seller (deducted from payout)
Bosta shipping — buyer share35%Buyer (added at checkout)
Stripe processing fee~2.9%Buyer (added at checkout)

So the buyer pays goods − discount + 35% of shipping + the Stripe fee; the seller's wallet nets the sale minus the 15%/10% commission and minus 65% of shipping.

Worked example — a 500 EGP basket

Subtotal 500 → commission 75 (15%), seller shipping share 32.5 (65%), buyer shipping share 17.5 (35%), Stripe fee 15.01. The buyer pays 532.51; the seller nets 392.5 into the wallet. (Verified against a live quote.)

Expert note — charged equals displayed

The discount is applied as a one-time Stripe coupon on the session, so the amount Stripe actually charges always equals the figure the quote displayed — there is no rounding drift between the cart and the receipt. Custom orders charge the Stripe fee on every milestone and add the 35% shipping share on the final one. Defaults: CommissionStandard .15, CommissionCustom .10, ShippingSellerShare .65, ShippingBuyerShare .35, StripeFeePercent .029, DefaultShipping 50 per store.

Platform capability

Seller wallet & payouts

Each seller wallet holds two buckets — a PENDING balance (money earned but not yet collectable) and an AVAILABLE balance (cleared, withdrawable) — plus an append-only ledger of every movement.

  • A sale lands in pending at fulfillment, then moves to available when the parcel is delivered.
  • A PAYOUT posts a negative available amount and is rejected if funds are insufficient.
  • A return reverses the original credit (SALE_REVERSAL), protecting the platform from paying out money for goods that came back.

The ledger is idempotent — each write carries a store-order-derived key, and a unique (wallet_id, idempotency_key) constraint is the real backstop against double-crediting. This is covered in depth in the Wallet idempotency deep dive.

Expert note — payouts in-house, not Stripe Connect

Bank details are stored in our own schema and only the last four digits are retained (GET /seller/wallet returns bankDetails { bankName, accountHolder, last4, configured }; set via POST /seller/wallet/bank-details). Stripe Connect onboarding was deliberately descoped: it would couple every seller to a Stripe-managed identity flow, whereas an in-house ledger keeps the marketplace modular and the demo self-contained. The trade-off — actual money movement to banks is manual/out-of-band — is an accepted, documented limitation.

Platform capability

Warehouses (pickup locations)

A seller can keep several pickup locations. Bosta always collects parcels from the seller's default warehouse; the first one is seeded automatically from the address on the store application.

CRUD — /api/v1/seller/warehouses
GET    /seller/warehouses                list
POST   /seller/warehouses                add
PUT    /seller/warehouses/{id}           edit
POST   /seller/warehouses/{id}/default   make this the pickup location
DELETE /seller/warehouses/{id}           remove (default promotes oldest survivor)

Fulfillment picks the pickup point with OrderByDescending(IsDefault).ThenBy(PickupId), so the chosen default is used and deletion never leaves a seller without one.

Expert note — a 1:1 table made 1:many

Originally store_pickup_addresses had a UNIQUE index on sellerid (one address per seller). To support multiple warehouses the unique index was dropped and label + is_default columns added (DDL run directly against the manzili schema; the table name is the plural store_pickup_addresses). The EF nav changed from a single StorePickupAddress to a StorePickupAddresses collection (WithMany), and exactly one default is enforced in WarehouseService.

Platform capability

Store verification

Becoming a seller is gated. A buyer applies (POST /stores/apply); an admin then approves or rejects the application, and only an approved & active store grants the seller role.

The gate lives in AuthService.DetermineRoleAsync: it returns the seller role and a sellerId claim only when StoreStatus == "approved" && IsActive. Pending, rejected or disabled applicants simply log in as a buyer; on approval they re-login (or a token refresh) to pick up the seller role.

  • GET /stores/my-application surfaces the caller's own status — { hasApplication, status, isActive, storeId, name } — so the apply page shows pending/approved/rejected instead of re-showing the form.
  • AdminService.UpdateStoreStatusAsync persists the new status + active flag and notifies the applicant on approve / reject / disable / enable.
Expert note — why gate at role resolution

Putting the check in DetermineRoleAsync means authorization flows from a single source of truth: the JWT's role/sellerId claims. No controller needs a bespoke "is this store approved?" guard — [Authorize(Roles="seller")] already can't be satisfied unless the store passed review.

Platform capability

Moderators & permissions

Admins come in two tiers. A super-admin can do anything; a moderator is an admin restricted to specific sections of the dashboard.

A moderator is just a systemadmin row whose Supervisorid points at a super-admin (full admins have Supervisorid = null). The seeded third admin smak is a moderator. Each moderator's reachable sections are rows in person_permission:

section codes
orders1 · products2 · stores3 · reports4 · requests5 · coupons6
EndpointWhoPurpose
GET /admin/meAny adminReturns { isSuperAdmin, permissions[] } — the UI hides links accordingly.
GET /admin/moderatorsSuper-admin onlyList moderators.
PUT /admin/moderators/{id}/permissionsSuper-admin onlySet a moderator's sections.
Expert note — enforced server-side, not just hidden

Hiding sidebar links is cosmetic; the real check is AdminService.EnsureSectionAsync(personId, section), invoked at the top of every admin mutation (product, store, report, coupon actions). A moderator must hold the matching section or it throws 403 FORBIDDEN; super-admins bypass the check. Moderator management itself is super-admin-only, so a moderator can never grant itself new sections.

Platform capability

Reports & chat monitoring

Any signed-in user can flag content with POST /reports (a real, persisted PENDING report — it used to be a fake client-side acknowledgement). Admins review the queue at GET /admin/reports and resolve via POST /admin/reports/{id}/action.

The admin report DTO is enriched with the reporter's name and the target's identifiers (productId / storeId / storeOrderId / customRequestId), so a moderator sees both who reported and what was reported.

Chat monitoring

Admins can read the buyer↔seller custom-order negotiations read-only through GET /admin/conversations and GET /admin/conversations/{id}.

Expert note — which table is the chat?

The negotiation chat is stored in OfferMessages (the offer thread), not the legacy Conversation/Message tables, which are unused. Reports reuse the timestamp without time zone handling described in the data layer gotcha — reports.created_at/resolved_at are written with DateTimeKind.Unspecified.

Health & logging

GET /api/v1/health returns { success, data: { status, database } } and performs a real CanConnectAsync() probe — use it for container liveness/readiness checks. Request logging is structured via Serilog (the equivalent of Node's morgan).

Expert note — provider chain & secrets

Configuration resolves in order json → user-secrets (Development only) → environment variables, last-wins. That means the committed appsettings.json carries no secrets, developers use user-secrets locally, and production overrides purely through env vars — the same binary in every environment.

Glossary

ORM (Object-Relational Mapper)
Maps database rows to objects so you query with code, not SQL. Here: EF Core (was Prisma).
DI (Dependency Injection)
The framework creates your objects and supplies their dependencies. You register services once and ask for them by type.
Middleware
A step in the request pipeline that can act before/after the next step — e.g. the exception handler, CORS, authentication.
DTO (Data Transfer Object)
A plain class describing the exact shape of a request or response, decoupled from database entities.
Claim
A key/value fact inside a JWT (e.g. role=seller) trusted after the signature is verified.
Scoped / Singleton (service lifetime)
Scoped = one instance per HTTP request (e.g. the DbContext). Singleton = one for the app's lifetime (stateless helpers).
DbContext
EF Core's gateway to the database — exposes DbSet<T> collections queried with LINQ.
Scaffolding (database-first)
Generating C# entities + a DbContext from an existing schema, rather than defining classes first.
Idempotency
An operation that yields the same result run once or many times — essential for safely retrying webhooks and payments.
