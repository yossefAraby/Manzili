The data behind Manzili.

A multi-vendor marketplace for handmade Egyptian products, persisted in a single PostgreSQL database on Supabase — schema manzili, ~45 tables, read and written by an EF Core database-first backend.

New to databases? Read this first

A relational database stores data in tables (like spreadsheets). Each row has a primary key (PK) that identifies it; a foreign key (FK) is a column that points at another table's primary key, which is how tables link together. Terms you don't recognise are defined in the Glossary; the rose-coloured Expert notes add depth and can be hidden with the control at the top right.

Expert note — one DB, two stacks

This is the same physical database the project's original Node/Prisma backend used; the .NET rebuild was scaffolded against it without reshaping it. Because the schema is owned upstream, the application uses no EF migrations — it treats the schema as read/write but never re-shapes it. Supabase also injects its own managed schemas (auth, storage, realtime, vault); the application maps only the manzili schema and references the Supabase enums/extensions just so the model validates.

The schema trap

Opening the project in the Supabase Table Editor shows an empty database — because the editor defaults to the public schema. Every Manzili table is under manzili. Switch the schema selector (or run SET search_path TO manzili;) to see the data.

The model was generated once with the EF Core scaffold command, pointed at the manzili schema:

bash — one-time scaffold
dotnet ef dbcontext scaffold "<connection>" Npgsql.EntityFrameworkCore.PostgreSQL \
  --schema manzili --context ManziliDbContext \
  --context-dir Persistence --output-dir Persistence/Entities --no-onconfiguring
Expert note — one schema fix was required

Scaffolding initially failed on a single FK type mismatch: custom_request.categoryid was integer while category.categoryid is smallint. A one-line ALTER COLUMN … TYPE smallint aligned the database with its own declaration so EF could map the relationship. Later DDL (run directly via Npgsql against the manzili schema) dropped the 1:1 unique index on store_pickup_addresses.sellerid and added label + is_default, turning warehouses into a 1:many.

The model

ER overview

The schema has one clear spine. A human is a person; the roles enduser (buyer), seller and systemadmin are 1:1 tables that extend it. Buyers browse a products catalog organised by category, fill a cart, and place an orders row that fans out into per-seller store_orders. Each store-order ships via a shipment and credits a seller_wallet. Made-to-order work flows through custom_request → offers → offer_payments.

Simplified spine. Custom orders (custom_request → offers → offer_messages / offer_payments), coupons (coupons → user_coupons), reviews, reports, notifications, addresses and warehouses hang off these core tables — browse them all in the Schema explorer below.

The core flows, in words

  • Identity. person ⊃ enduser / seller / systemadmin (each 1:1). person_permissions grants moderators section access; systemadmin.supervisorid is a self-reference distinguishing super-admins from moderators.
  • Catalog. products belong to a seller and a category, with product_images, product_variants → variant_options.
  • Cart & wishlist. The cart is now account-linked and persisted server-side — cart carries an items_json text column holding the active cart snapshot (added idempotently by the app's SchemaMigrator); the legacy cart_contain M:N junction still exists. wishlist + whishlist_contain.
  • Orders & fulfillment. orders → store_orders → store_order_items; each store-order gets one shipment with a shipment_events timeline; returns + proof_as_images handle reverse logistics.
  • Payments & wallet. seller_wallet (pending/available) ← wallet_transactions ledger; payout drains the available balance.
  • Custom orders. custom_request (+ visual_inspiration, voicememo, color_palette) → offers → offer_messages + offer_payments.
  • Coupons. coupons (+ coupon_product) and the redemption record user_coupons.
  • Reviews & reports. reviewing_and_rating (one per buyer+product); reports for moderation.
  • Messaging & misc. notification; conversation + messages (legacy chat, superseded by offer messages); addresses with Bosta city/zone/district ids; bosta_address_mapping.

Design

Key relationships & design decisions

Identity as supertype / subtype

A single human is one person (PK personid, unique email). The three roles are separate tables in a 1:1 relationship with person: enduser, seller, systemadmin — each has a unique FK back to personid. A person can be a buyer and a seller at once (two role rows, one identity). Moderators are modelled with systemadmin.supervisorid (self-FK: a moderator points at the super-admin who created them) plus person_permissions rows granting section access.

Expert note

This is classic supertype/subtype (a.k.a. "table-per-type" inheritance). Shared columns — email, password, names, refresh token — live once on person; role-specific columns live on the subtype. The .NET role resolver simply asks "is there a systemadmin row? a seller row?" to derive the JWT role, and seller verification gates that: a seller only counts as a logged-in seller when store_status='approved' and is_active.

The per-seller order split & price snapshots

The single most important design decision. A buyer's cart can contain items from multiple independent sellers, but each seller fulfils, ships and is paid separately. So one purchase becomes:

model
orders            (buyer, address, payment method/status, grand total, coupon_snapshot)
 ├─ store_orders  (seller A)  subtotal/discount/shipping/total, own status
 │   └─ store_order_items[]   price_at_purchase + product_name + product_image_url snapshot
 └─ store_orders  (seller B)  …
     └─ store_order_items[]
  • orders holds buyer-level facts (one address_id, one payment, the grand total, a JSON coupon_snapshot).
  • store_orders is the unit a seller sees and acts on: its own status, subtotal, discount_total, shipping_total, total.
  • store_order_items snapshots the price, name and image at purchase time, so order history survives later product edits or deletions.
Expert note — two item tables co-exist

The legacy consist_of (a junction of orders×products with price_at_purchase) still exists, but the live order path writes per-seller line items into store_order_items. The snapshot columns are deliberate denormalization for an audit/history concern — the line item must remain truthful even if the product's price changes or the product is removed (hence the RESTRICT on the product FK).

The wallet ledger & idempotency

Each seller has exactly one seller_wallet (unique sellerid) with two money buckets: pending_balance and available_balance. Every movement is an append-only row in wallet_transactions (SALE_CREDIT, COMMISSION_DEBIT, SHIPPING_DEBIT, releases, reversals, payouts). Funds land pending on sale and release to available on delivery.

constraint
UNIQUE (wallet_id, idempotency_key)   -- wallet_transactions
-- a webhook retry with the same key hits the constraint; the duplicate
-- insert AND its balance change roll back together. Money is never double-counted.
Expert note

The seller.sellerwallet_balance column survives from the original design as a convenience scalar, but the authoritative balances are the wallet's two buckets, reconstructable by summing the ledger. Ledger rows are only ever inserted, never updated — the immutable-ledger pattern. payout rows drain the available balance and are rejected when funds are insufficient.

Custom-order negotiation with milestones

Made-to-order work is a negotiation, not a fixed-price purchase. A buyer files a custom_request (dimensions, material, desired date, plus visual_inspiration images, a voicememo, and a color_palette). Sellers respond with offers (price + description). The accepted offer carries a state machine of timestamps — accepted_at, first_paid_at, progress_uploaded_at, ready_to_ship_at, second_paid_at — and a running chat in offer_messages. Each milestone payment is an offer_payments row.

Expert note

Paying the final milestone bridges back into the standard pipeline: the app creates a real orders + store_orders (with a hidden, disabled placeholder products row, because store_order_items requires a product FK) and then runs the same shipment + wallet flow. That is why custom orders and standard orders share fulfillment without duplicating it.

Pickup warehouses as 1:many

A seller can ship from several locations. store_pickup_addresses was originally 1:1 with the seller; it is now 1:many — the unique index on sellerid was dropped and label + is_default were added. Fulfillment picks the default warehouse for the Bosta pickup leg.

Referential integrity & delete behavior

Relationships are enforced by named FK constraints. Delete behavior is chosen per relationship, visible in the mappings: products → seller is CASCADE (deleting a seller removes their products); store_order_items → products and store_orders → seller are RESTRICT (you cannot delete a product/seller out from under a live order); buyer-facing FKs such as orders → enduser/address are SET NULL so order history outlives a deleted account or address.

⚠️ The timestamp-without-time-zone gotcha

Several tables store timestamps as timestamp WITHOUT time zone rather than timestamptz — notably coupons (created_at, expired_date), reports (created_at, resolved_at), notification.created_at, and store_pickup_addresses. Npgsql throws if you write a DateTime with Kind=Utc into such a column. Writes must use DateTimeKind.Unspecified (and the read path re-specifies UTC). This bit the team repeatedly — every notification create was silently 500-ing until it was fixed.

snake_case columns, PascalCase entities

The database uses snake_case column names (first_name, created_at, store_orderid). The scaffolded C# entities use PascalCase (FirstName, CreatedAt, StoreOrderid) with explicit HasColumnName(...) mappings, so the two never have to match by convention.

Expert note — naming quirks preserved

The schema carries a few historical spellings that the scaffold faithfully preserved rather than "fix": wichlistid/whishlist_contain (wishlist), tittle (notification title), matrial/lenght/hight on custom_request. Renaming a column in a database-first project means a real migration and a code change, so they were left as-is. Composite primary keys are common on junctions and weak entities (cart_contain, reviewing_and_rating, product_images, color_palette, voicememo).

Design

Active DB vs the ERDPlus design

The team began with a normalized paper model in ERDPlus (33 entities). The database that actually shipped is the implemented, integration-shaped schema (~45 tables). This section is an honest, table-by-table account of how the design evolved — what was kept, what changed, and what reality forced the team to add.

Why two are different — and that's fine

An ER diagram is a design artifact: it captures entities and relationships before you know exactly how payments, shipping or a payment provider behave. The live schema is what survived contact with Stripe, Bosta, a multi-vendor cart and a moderation workflow. Divergence is expected and healthy; the question a panel cares about is whether you can explain each change.

What the live DB added that the ERD lacked

  1. Wallet ledger. The ERD modelled seller money as a single SellerWallet_Balance FLOAT on SELLER. The live DB adds a full seller_wallet (pending/available buckets, bank details, currency) plus an append-only, idempotent wallet_transactions ledger and keeps payout — money is now auditable, not a mutable number.
  2. Full fulfillment. shipment became per-store-order and Bosta-integrated (tracking number, AWB url, carrier, COD amount, status), and a brand-new shipment_events table records a webhook-deduplicated timeline.
  3. Custom-order negotiation. offers, offer_messages and offer_payments replace the generic CONVERSATION/MESSAGES, adding milestone timestamps and per-milestone payments.
  4. Warehouses. store_pickup_addresses (1:many, with label + is_default) — sellers can ship from multiple locations.
  5. Moderators. person_permissions + systemadmin.supervisorid implement section-scoped moderator roles under super-admins.
  6. Bosta integration columns. bosta_city_id / bosta_zone_id / bosta_district_id on addresses (and pickup addresses), plus a bosta_address_mapping lookup table.
  7. Reports. A real reports table (reporter, target product/store/store-order/request, reason, admin note, status) for moderation.
  8. Variants & payment metadata. product_variants/variant_options, and Stripe metadata on orders (stripe_payment_intent_id, psp, transaction_ref).
  9. Account-linked cart snapshot. An items_json text column on cart holds the buyer's active cart server-side, so it survives logout and follows the account across devices (no longer kept in the browser). Added idempotently by the app's SchemaMigrator.

The headline evolutions, explained

1 — Payment on ORDER → per-seller STORE_ORDER split

The ERD put every payment field directly on a single ORDER (with STANDARD_ORDER / CUSTOMIZED_ORDER subtype tables). That works for a single-vendor shop, but Manzili is multi-vendor: a cart can mix sellers, and each seller must be paid, shipped and statused independently. The live DB keeps orders as the buyer-level envelope (one payment, one address) and introduces store_orders + store_order_items for the per-seller reality. The ERD's subtype tables survive as thin markers, but the substantive money moved down to the store-order.

2 — A float balance → a wallet + ledger

A single mutable FLOAT balance cannot answer "why is this seller owed X?" and is unsafe under concurrent webhooks. The live design replaces it with two explicit buckets and an immutable ledger keyed by (wallet_id, idempotency_key), so every credit, commission, shipping deduction, release and payout is a permanent, replay-safe row. (Also: money moved from FLOAT to numeric(12,2).)

3 — Generic chat → offer-centric negotiation

The ERD's CONVERSATION/MESSAGES were a generic buyer↔seller chat. Real commissions needed a price, an accept event, progress proof and staged payments — so the live DB hangs the chat (offer_messages) and payments (offer_payments) directly off an offers row that carries the milestone state machine. The old chat tables remain but are unused.

4 — Other shifts

  • Warehouses went from absent to a 1:many store_pickup_addresses.
  • Moderators went from absent to person_permissions + a supervisor self-FK.
  • Bosta ids were added to addresses so shipping can resolve to a carrier's geography.
  • The ERD's STANDARD_ORDER / CUSTOMIZED_ORDER subtypes are retained but de-emphasised; the live system distinguishes order kind mainly through the store-order pipeline and the custom-offer bridge.
Expert note — be fair about ERD quirks

The ERDPlus export shows the usual early-design roughness, and it's worth naming them plainly rather than hiding them: several columns are INT placeholders that became real types (SHIPMENT's Carrier/Status/Shipped_at_time/Tracking_Number were all INT; ORDER's money fields were INT); ADDRESSES.Street VARCHAR(4) and BuildingNumber VARCHAR(6) are implausibly small; a couple of labels are misspelled (Stauts, Canrnier, Delivered_at_tiime). None of this is a knock on the design — it's a normalized paper model whose job was to get the entities and relationships right, which it did. The live schema is the same model after it met exact types, a payment provider, a courier and a moderation workflow.

Reference

Glossary

Primary key (PK)
The column (or set of columns) that uniquely identifies each row in a table. Here usually a surrogate auto-increment integer like orderid.
Foreign key (FK)
A column that references another table's primary key, enforcing that the referenced row exists. This is how tables link — e.g. products.sellerid → seller.sellerid.
Normalization / 3NF
Organising tables so each fact lives in one place, removing redundancy and update anomalies. Third normal form (3NF) means non-key columns depend on the key, the whole key, and nothing but the key.
Junction (associative) table
A table that resolves a many-to-many relationship into two one-to-many's, typically with a composite key — e.g. cart_contain (cart × product) or follow (enduser × seller).
Supertype / subtype
An inheritance pattern: a general entity (the supertype, person) and specialised entities (the subtypes, enduser/seller/systemadmin) that share its identity via a 1:1 FK.
Ledger
An append-only record of every transaction. Balances are derived from the ledger rather than overwritten, giving a full, auditable history — see wallet_transactions.
Idempotency key
A unique token attached to an operation so that repeating it (e.g. a retried webhook) has the same effect as doing it once. Enforced here by a unique (wallet_id, idempotency_key) index.
timestamptz vs timestamp
timestamptz stores an instant in UTC and converts on read; plain timestamp stores wall-clock time with no zone. Mixing them — and writing a UTC-kind value into a plain timestamp — is the gotcha that bit this project.
ORM / scaffolding
An Object-Relational Mapper (here EF Core) maps table rows to objects so you query with code. "Scaffolding" (database-first) generates those entity classes and the DbContext from an existing schema, instead of writing classes first.
