Frontend documentation

The Manzili storefront, in Next.js.

The customer-facing marketplace for handmade Egyptian products — a Next.js 16 App Router application on React 19 that talks to the .NET API over a single typed HTTP layer, with Redux Toolkit holding the client-side state.

New to Next.js? Read this first

This is the frontend — the website a buyer or seller opens in their browser. It renders the pages and forms, then calls the separate .NET backend for all data. Routes are defined by the folder structure under app/ (App Router), not a route table. Unfamiliar terms are in the Glossary; the rose-coloured Expert notes add depth and can be hidden with the control at the top right.

Expert note

This is a pure client of the API: after the migration off localStorage and dummy data, the app holds no business logic and no database. Most pages are client components ("use client") because they read Redux and the session; data is fetched on the client through lib/api/* rather than in React Server Components. Auth is httpOnly-cookie based — tokens live in cookies the browser sends automatically, never in JS/localStorage. The one server surface that remains is app/api/ai/* — thin route handlers that proxy LLM calls for the custom-order form so provider keys never reach the browser.

Quick start

You need Node.js and the .NET backend running (see the backend doc). Run the frontend from frontend/Manzili — not the repository root.

bash
cd frontend/Manzili
npm install
npm run dev                 # Next.js dev server on http://localhost:3000

# build / serve the production bundle
npm run build
npm start

Point the app at the API with a .env.local file. Only variables prefixed NEXT_PUBLIC_ are exposed to the browser:

.env.local
# Base URL of the .NET API (defaults to the local dev backend if unset)
NEXT_PUBLIC_API_BASE_URL=http://localhost:5080/api/v1

# Optional server-side keys for the custom-order AI helper (app/api/ai/*)
ZAI_API_KEY=...
GEMINI_API_KEY=...
GROQ_API_KEY=...
CORS

The browser calls the API directly, so the backend must allow this origin. The .NET Manzili:CorsOrigin setting already permits http://localhost:3000 and :3001 in development. A new deployed origin must be added there or requests will be blocked by the browser.

Expert note — what's deliberately absent

No data-fetching library (React Query/SWR), no form library, no component kit, and no prisma/stripe packages — those were removed when business logic moved to the backend. Architecture

Pages, state, and one API layer

Three concerns, cleanly separated: the App Router renders pages, Redux holds UI state, and a single HTTP layer is the only thing that talks to the backend.

app/ — the App Router

Folders define routes; page.jsx is a page, layout.jsx wraps a subtree. Three route groups partition the app, each with its own chrome. Most pages opt into the client with "use client" so they can use Redux and the browser-stored token.

components/

Reusable UI — Navbar, Hero, ProductCard, OrderSummary, TrackingTimeline, plus the store/ and admin/ layout/sidebar shells.

lib/features/ — Redux slices

One slice per concern, each owning its state, reducers, and async thunks (the thunks call lib/api). Selectors live alongside the slice so every consumer derives state the same way.

lib/api/ — the HTTP layer

The only code that touches the network. client.js is the shared fetch wrapper; one module per backend area (products, orders, custom, seller, admin, …) adapts the API's DTOs into the shapes the UI expects.

Expert note — the adapter seam

Every API module exports small adapt*() functions that map a backend DTO to a UI object (e.g. adaptProductCard, adaptOrder, adaptNotification turning isRead → read). This anti-corruption seam means a field rename on the backend is absorbed in one place rather than rippling through components — and it's why the UI survived the whole Node→.NET port unchanged.

Server vs client components

What's the difference?

In the App Router every component is a Server Component by default — it renders once on the server and ships only HTML, with no JavaScript and no access to the browser. Adding "use client" at the top makes it a Client Component: it runs in the browser, so it can use useState, event handlers, Redux, and localStorage.

Because Manzili is an interactive, session-driven app, most pages are client components. They need the Redux store, the cookie-backed session, and effects that fetch through lib/api after mount. The few server pieces are the root layout's metadata and the app/api/ai route handlers, which run server-side so API keys stay off the client.

Expert note — the provider boundary

The root layout.jsx is a Server Component (it exports metadata), but it renders <StoreProvider> and <LocaleProvider>, both "use client". That's the standard pattern: keep the layout on the server for metadata and fonts, then drop into client context providers for everything below. <html> carries suppressHydrationWarning because the locale effect can adjust documentElement.lang after hydration.

Core concept

The API client

lib/api/client.js is the single chokepoint for every backend call. It prepends the base URL, sends the httpOnly auth cookie with the request, unwraps the envelope, and recovers from an expired access token transparently.

JS — base URL + cookie-based auth
const BASE_URL = (process.env.NEXT_PUBLIC_API_BASE_URL || 'http://localhost:5080/api/v1').replace(/\/$/, '');

async function rawFetch(path, { method = 'GET', body, headers = {}, auth = true } = {}) {
  const finalHeaders = { ...headers };
  // FormData (image uploads) is sent as-is; everything else is JSON.
  if (body != null && !(body instanceof FormData)) {
    finalHeaders['Content-Type'] = 'application/json';
    body = typeof body === 'string' ? body : JSON.stringify(body);
  }
  // No Authorization header: the JWT rides an httpOnly cookie (manzili_at) the
  // browser attaches automatically. credentials:'include' sends it cross-origin.
  return fetch(`${BASE_URL}${path}`, { method, headers: finalHeaders, body, credentials: 'include' });
}

401 → refresh → retry

On a 401 the client runs the refresh-token flow once, then replays the original request. The refresh cookie is sent automatically; a shared refreshPromise de-duplicates concurrent refreshes so a burst of 401s triggers a single token exchange. If refresh fails, the session is cleared (effectively a logout).

JS — the retry path
export async function apiFetch(path, options = {}) {
  const { retry = true, auth = true } = options;
  let res = await rawFetch(path, options);

  if (res.status === 401 && retry && auth) {
    const refreshed = await tryRefresh();      // POST /auth/refresh (cookie), single-flight
    if (refreshed) res = await rawFetch(path, options);   // replay once
  }

  const text = await res.text();
  const json = text ? JSON.parse(text) : null;
  if (!res.ok || json?.success === false) {
    const err = json?.error || {};
    if (res.status === 401) clearSession();    // give up → logout
    throw new ApiError(err.message || `Request failed (${res.status})`,
      { code: err.code || `HTTP_${res.status}`, status: res.status, details: err.details });
  }
  return json ?? { success: true, data: null }; // full envelope back to the caller
}

Verb helpers & anonymous calls

Thin wrappers return the full envelope; callers read .data and any top-level meta. Public endpoints opt out of the token with { auth:false }.

JS
export const apiGet    = (p, o) => apiFetch(p, { ...o, method: 'GET' });
export const apiPost   = (p, b, o) => apiFetch(p, { ...o, method: 'POST',   body: b });
export const apiPut    = (p, b, o) => apiFetch(p, { ...o, method: 'PUT',    body: b });
export const apiPatch  = (p, b, o) => apiFetch(p, { ...o, method: 'PATCH',  body: b });
export const apiDelete = (p, o) => apiFetch(p, { ...o, method: 'DELETE' });

// anonymous (no Authorization header):
await apiPost('/auth/login', { email, password }, { auth: false });
await apiPost('/contact',    payload,             { auth: false });
Expert note — typed errors & the envelope contract

Failures throw a single ApiError carrying { message, code, status, details } lifted straight from the backend's error object, so a component can branch on err.code or render err.details field errors without parsing strings. The success path returns the envelope verbatim — meta like total/page sits at the top level next to data, exactly matching the backend's response envelope.

State management

Global UI state lives in a Redux Toolkit store assembled in lib/store.js and provided by app/StoreProvider.js. Eight slices, each owning one concern.

Selectors derive the role

Rather than store a role flag that could drift, the role is computed from the session in authSlice.js:

JS — authSlice selectors
export const selectIsLoggedIn = (s) => Boolean(s.auth.session?.userId);
export const selectIsAdmin    = (s) => s.auth.session?.role === 'admin';
export const selectIsSeller   = (s) =>
  Boolean(s.auth.session?.userId && s.auth.session?.storeId) &&
  s.auth.session?.role !== 'admin';      // seller ⇔ has an approved store's storeId

Persistence — nothing sensitive in the browser

The session is carried by httpOnly cookies, so it is not stored in localStorage; on boot the app resolves who you are by calling the API (GET /auth/me). The cart is account-linked and persisted server-side — loaded from the API on login and synced back, so it survives logout and follows the account across devices. Addresses, notifications, wishlist, and the catalog are likewise hydrated from the API after mount, so the browser never holds stale server data. The product catalog is fetched once at app bootstrap, so home / cart / wishlist are never empty before a visit to /shop. (A guest's in-session cart is merged into the account on sign-in.)

JS — app/StoreProvider.js (abridged)
export default function StoreProvider({ children }) {
  const storeRef = useRef();
  if (!storeRef.current) storeRef.current = makeStore();
  useEffect(() => {
    const store = storeRef.current;
    store.dispatch(fetchProducts());           // load the catalog once at bootstrap
    // cookie-backed session: ask the API who we are, then hydrate the server cart
    store.dispatch(resolveSession()).then(() => store.dispatch(hydrateCart()));
  }, []);
  return <Provider store={storeRef.current}>{children}</Provider>;
}
Expert note — store per request, single-flight hydration

makeStore() is a factory (not a module-level singleton) so each browser session gets a fresh store and SSR never leaks state between requests; the ref guard ensures it's created once per mount. The session is resolved from the cookie via the API rather than read synchronously from storage. Hydration thunks are dispatched by the components that need the data (e.g. NotificationBell dispatches hydrateNotifications) and are gated on selectIsLoggedIn, so a guest never fires authenticated requests.

Core concept

Auth & session

Login and register call the API; the server sets the auth tokens as httpOnly cookies, and the response body carries the user so the app can map it onto its session shape. A separate admin portal posts to a different endpoint and gets its own cookie pair.

JS — lib/api/auth.js
function toSession(user) {                       // backend user → app session
  const storeId = user.storeId ? String(user.storeId) : null;
  return { userId: String(user.id), name: user.name || '', email: user.email || '',
           storeId, role: user.role || (storeId ? 'seller' : 'buyer') };
}

export async function apiLogin({ email, password }) {
  // the server sets manzili_at + manzili_rt as httpOnly cookies on the response
  const res = await apiPost('/auth/login', { email, password }, { auth: false });
  return toSession(res.data.user);
}
export async function apiAdminLogin({ username, password }) {        // distinct portal
  // sets the SEPARATE admin cookie pair (manzili_admin_at/_rt), scoped to /api/v1/admin
  const res = await apiPost('/admin/auth/login', { username, password }, { auth: false });
  return toSession(res.data.user);               // role === 'admin'
}
export async function apiLogout()      { await apiPost('/auth/logout');       } // clears the cookies server-side
export async function apiAdminLogout() { await apiPost('/admin/auth/logout'); }

Token storage — httpOnly cookies

The access and refresh tokens are httpOnly cookies set by the API, never touched by JavaScript and never in localStorage — so page scripts can't read them and XSS can't exfiltrate them. The browser attaches them automatically (credentials:'include'), and the app learns the session by calling GET /auth/me rather than reading a token.

Admin and buyer/seller sessions are isolated

Buyer/seller cookies (manzili_at/manzili_rt) are scoped to path /; the admin portal uses a separate pair (manzili_admin_at/manzili_admin_rt) path-scoped to /api/v1/admin. The two sessions can coexist in one browser, and logging into the admin console no longer clobbers a signed-in buyer or seller (this fixed a real bug).

Role gating

  • Seller dashboard (app/store/*): StoreLayout checks session.userId + session.storeId and otherwise shows a sign-in prompt. Crucially, the backend only grants a storeId when the store is approved and active — so a pending applicant logs in as a buyer and must re-login (or token-refresh) once approved.
  • Admin console (app/admin/*): AdminLayout gates on selectIsAdmin, redirects to /admin/login if not, and loads GET /admin/me to get { isSuperAdmin, permissions[] }; AdminSidebar filters links by permission and moderators are bounced off sections they don't hold.
Two separate logins

Buyers/sellers use /login (email + password → /auth/login); admins use /admin/login (username + password → /admin/auth/login). The admin endpoint only succeeds for accounts backed by a systemadmin row, returning a session with role:"admin".

Core concept

Internationalization

i18n is hand-rolled — no library. Two dictionaries (lib/i18n/dictionaries/en.js and ar.js) sit behind a LocaleContext exposing a t() translate function with dotted-key lookup, English fallback, and {param} interpolation.

JS — lib/i18n/LocaleContext.jsx
const t = useCallback((key, params = {}) => {
  const dict = dictionaries[locale] || en;
  let value = getDeepValue(dict, key) ?? getDeepValue(en, key);   // fallback to English
  if (value == null) return key;
  return String(value).replace(/\{(\w+)\}/g, (_, p) =>
    params[p] !== undefined ? String(params[p]) : `{${p}}`);       // {name} interpolation
}, [locale]);

// usage in a component:
const t = useTranslate();
<h1>{t('hero.headline')}</h1>

The chosen locale persists to localStorage under manzili_locale; the brand renders as منزلي in Arabic.

Deliberate: the UI stays LTR even in Arabic

Switching to Arabic translates the copy but does not flip the layout to RTL — setLocale always sets documentElement.dir = "ltr", and the root <html> is hard-coded dir="ltr". This is an intentional design decision (verified: documentElement.dir === 'ltr' in Arabic), keeping the visual layout identical across languages.

Expert note — live vs dead keys

Only keys read by client components are live. Some content pages (privacy-policy, about) are written as plain server/JSX content, so their privacyPolicy/about dictionary keys are effectively dead; the FAQ keys are live. The Arabic overhaul standardised the brand to منزلي everywhere and fixed two duplicate/typo keys in ar.js.

User flows

Key user flows

The five journeys that define the product. Switch tabs to walk each one.

Browse → product → cart → Stripe checkout

  1. Browse / search. /shop lists products via fetchProducts (the product slice); ShopFilters drive category/sort; full-text search hits GET /search.
  2. Product. /product/[productId] renders ProductDetails — gallery, variant picker, per-variant stock, ratings, a wishlist heart and a ReportButton. "Add to cart" dispatches addToCart; "Customize this item" stashes a seed and routes to the custom form.
  3. Cart. /cart shows the account-linked cart keyed by product+variant; OrderSummary calls quoteCheckout (POST /checkout/quote) so the displayed breakdown — subtotal − discount + 35% Bosta share + Stripe fee — equals what the card will be charged, and lets the buyer pick/add an address and apply a coupon.
  4. Checkout. createCheckoutSession (POST /checkout) returns a hosted Stripe URL; the browser redirects there. No card data ever touches this app.
  5. Success. Stripe redirects back to /cart/success (and the orders page) with ?session_id=; the app calls confirmCheckout (POST /checkout/confirm), which is idempotent and finalizes fulfillment even if the webhook never reached the dev machine.

Custom-order request → negotiation/offers → milestone payments

  1. Request. /custom/custom-form collects item, category, description, materials, reference photos; the AI helpers (below) suggest a prompt and review questions. A private request can target one vendor via a picker backed by GET /stores/search?q=&limit= (approved, active stores matched by store name or @username, straight from the seller table). Submitting calls createRequest (POST /custom/requests); drafts autosave to localStorage per user.
  2. Offers / chat. /custom/request-view/[id] and /custom/negotiation/[id] show offers (fetchOffers) and an offer chat (fetchOfferMessages / sendOfferMessage). The buyer accepts/declines via transitionOffer (PATCH /custom/offers/{id}).
  3. Milestone payments. Offers over the split threshold pay in milestones. createOfferCheckout (POST /custom/offers/{id}/checkout) opens a Stripe portal for a milestone; the request view confirms on the ?session_id= return; payOfferMilestone remains a direct fallback. Paying the final milestone creates the real order on the backend.

Orders, Bosta tracking, returns

  1. Orders. /orders lists the buyer's orders (fetchOrders) and, on a ?session_id= return, confirms a just-paid Stripe checkout. The DTO includes a per-vendor storeOrders[] breakdown (each with storeName, items incl. imageUrl, its delivery total and shipment/tracking) plus the delivery address, so the page renders one rich card per vendor with item thumbnails, per-vendor delivery and a status timeline. Online-payment orders only appear once paid — unpaid/abandoned and canceled orders are filtered out (COD shows immediately).
  2. Tracking. Each store-order carries a shipment { trackingNumber, carrier, status, events[] } object; TrackingTimeline renders it as a vertical Bosta timeline (or a compact inline row in tables).
  3. Returns. /returns and the orders page let a buyer request a return via requestReturn (POST /orders/{orderId}/return); the backend books a reverse Bosta delivery and the timeline gains a return requested event.

Seller dashboard

Under /store/*, gated by StoreLayout on an approved store. Pages: dashboard (fetchDashboard + a recharts orders chart), add/manage products (create/update/deleteSellerProduct, images via POST /upload), orders (status transitions via updateOrderStatus), returns, custom orders, coupons, wallet (balances, ledger, payout request, bank details), warehouses (multiple pickup locations with a default), and store settings. The seller orders list shows only real (paid or COD) orders — unpaid/abandoned online attempts and canceled orders are filtered out. The store username is fixed at creation and read-only in settings. Applicants who aren't yet approved see their verification status from GET /stores/my-application on /create-store.

Admin console

Under /admin/*, gated by AdminLayout. /admin/login → dashboard stats; approve/stores approve or toggle stores (storeAction), products disable products, orders + requests are read-only lists, reports resolve user reports (reportAction), coupons manage global coupons, moderators (super-admin only) toggle per-section permissions, and conversations is a read-only view of custom-order negotiation chats.

Don't forget CORS & HTTPS

The deployed frontend origin must be added to the backend's Manzili:CorsOrigin list, and the API base URL should be HTTPS in production so the browser doesn't block mixed content.

Expert note — image optimization & dev tuning

next.config.mjs sets images.unoptimized = true (images come from Cloudinary/remote URLs, so the Next image optimizer is bypassed) and tunes dev watchOptions/onDemandEntries to reduce RAM and disk churn on large working trees. Builds use the Webpack compiler explicitly via the --webpack flag.

Glossary

App Router
Next.js's routing system where folders under app/ define routes; page.jsx is a page and layout.jsx wraps a subtree.
Route group
A folder named in parentheses (e.g. (public)) that shares a layout but adds no URL segment.
Server / Client Component
Server Components render on the server and ship no JS by default; adding "use client" makes a component run in the browser with state, effects, and DOM access.
Hydration
React attaching event handlers and state to the server-rendered HTML in the browser, making a static page interactive.
Hydration warning
A mismatch between server HTML and the first client render. Suppressed on <html> here because the locale effect can change lang after mount.
Redux slice
A self-contained piece of the store — its state plus reducers — created with RTK's createSlice.
Selector
A function that reads (and derives) a value from the store, e.g. selectIsSeller. Keeps derivation logic in one place.
Thunk
An async action creator (RTK's createAsyncThunk) — here, the functions that call lib/api and update a slice, e.g. hydrateWishlist.
JWT / refresh token
A short-lived access token plus a longer-lived refresh token exchanged for a new pair when the access token expires. Here both ride httpOnly cookies the browser sends automatically — not a Bearer header.
Response envelope
The backend's uniform JSON shape { success, data, …meta } that the API client unwraps for every call.
SSR / CSR
Server-Side Rendering produces HTML on the server; Client-Side Rendering builds the UI in the browser. Manzili is mostly CSR behind client components.
Route handler
A server-side endpoint defined by a route.js file under app/api/* — here, the AI proxy routes.
